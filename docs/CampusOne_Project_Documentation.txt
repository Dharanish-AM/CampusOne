Abstract

Campus operations across most engineering colleges remain fragmented across disconnected systems — a separate attendance register, a manual bus-tracking WhatsApp group, a paper-based complaint log, and email threads for placement updates. CampusOne proposes a single, unified, AI-powered mobile and web platform that consolidates twenty core campus services — academics, transport, placements, hostel life, library, health, and community — into one role-based super app for students, faculty, administrators, transport staff, placement officers and club coordinators.

The system is built on the MERN-adjacent stack (React Native for mobile, React for the admin web portal, Node.js/Express for the backend, and MongoDB for persistence), augmented with Redis for caching, Socket.IO for real-time features such as live bus tracking and instant notifications, and a Retrieval-Augmented Generation (RAG) based AI assistant that allows natural-language queries about timetables, attendance, and campus logistics. The platform demonstrates practical application of full-stack engineering, real-time systems, role-based access control, cloud storage integration, and applied AI — while remaining extensible enough to evolve from an academic prototype into a production-grade deployment for actual institutional use.

This document details the problem statement, requirement analysis, system design, module-level specification, technology justification, implementation plan, and testing strategy for the CampusOne platform, along with a phased roadmap for scaling the system beyond the initial academic submission.

1. Introduction

1.1 Overview

CampusOne is an AI-powered smart campus super app designed to replace the patchwork of disconnected tools (paper registers, WhatsApp groups, spreadsheets, and multiple portals) that most colleges rely on today. It brings attendance, timetables, transport, placements, hostel management, library services, fee payments, and community features into a single mobile-first application accessible to every stakeholder on campus.

1.2 Problem Statement

Students and staff at most engineering colleges must navigate 5–10 separate systems to accomplish routine tasks: checking attendance on one portal, tracking the college bus over a phone call or informal group chat, applying for placements over email, and raising hostel or infrastructure complaints via paper forms. This fragmentation causes information delays, poor visibility for administrators, and a disjointed experience for students. There is no single, extensible, role-aware platform that unifies these campus services while remaining feasible to build and demonstrate as an academic project.

1.3 Objectives

To design and develop a unified role-based platform serving students, faculty, admin, transport staff, placement officers, and club coordinators.

To provide real-time visibility into attendance, timetables, and bus location.

To digitize placement, library, fee, hostel and complaint workflows currently handled manually.

To integrate an AI-based conversational assistant that answers campus-related queries using Retrieval-Augmented Generation (RAG).

To design the system with a modular architecture that allows incremental scaling from an academic prototype to a production-ready deployment.

1.4 Scope of the Project

The complete CampusOne vision spans twenty modules described in Section 6. For the purposes of academic submission within a two-semester final-year project timeline, development effort is organised into a Core Phase (modules essential for a working, demonstrable system) and a Roadmap Phase (modules documented in full but implemented as extensions beyond the initial submission). This phased scope is detailed in Section 9 (Implementation Plan) and ensures the delivered system is fully functional end-to-end rather than partially built across all twenty modules.

3. System Analysis

3.1 Existing System

Most institutions currently rely on a combination of a legacy ERP for attendance and fees, manual or semi-digital processes for hostel and complaint management, and informal communication channels (calls, messaging apps) for transport and notices. Placement coordination is typically handled through spreadsheets and email.

3.2 Proposed System

CampusOne replaces this fragmented landscape with a single mobile and web platform offering real-time data, role-based dashboards, and an AI assistant layer that lets users retrieve information conversationally instead of navigating multiple menus. All twenty modules share a common authentication, notification, and data layer, eliminating duplicate data entry and inconsistent records.

3.3 Feasibility Study

3.3.1 Technical Feasibility

The proposed stack (React Native, React, Node.js/Express, MongoDB, Redis, Socket.IO) is mature, well-documented, and directly aligned with skills already demonstrated in prior full-stack projects, making technical execution feasible within an academic timeline for the Core Phase modules.

3.3.2 Economic Feasibility

All core components (MongoDB Community, Redis, Node.js, React Native/Expo, Docker, GitHub Actions) are open-source or available on free tiers. Paid dependencies are limited to optional cloud storage, maps, and LLM API usage, which can be developed and demonstrated using free-tier quotas.

3.3.3 Operational Feasibility

The system is designed for non-technical end users (students, faculty, hostel/transport staff) through a simple, mobile-first interface, minimising training overhead for real-world adoption.

5. System Design

5.1 System Architecture

CampusOne follows a layered client-server architecture: mobile and web clients communicate with a Node.js/Express API gateway over REST and WebSocket protocols. The gateway delegates requests to core backend services, a dedicated real-time service for live features, and an AI service layer that performs Retrieval-Augmented Generation over a vector database. Data is persisted in MongoDB, cached in Redis, and media is stored in AWS S3 / Cloudinary. The architecture is containerized with Docker and fronted by Nginx, with GitHub Actions handling CI/CD.

5.2 Data Flow Overview

Client apps authenticate via the Auth Service and receive a short-lived JWT access token plus a refresh token.

Role-based middleware on the API gateway restricts each endpoint to permitted roles (Student, Faculty, Admin, Transport Staff, Placement Officer, Club Coordinator).

Real-time events (bus location updates, new notices, complaint status changes) are pushed via Socket.IO channels scoped per user/role.

AI Assistant queries are routed to the AI Service, which retrieves relevant context from the vector database (e.g., the student&apos;s own timetable/attendance records) before generating a grounded response.

Scheduled jobs (attendance shortage calculation, fee due reminders, library due-date reminders) run as background workers and trigger FCM push notifications.

The stack was selected for three reasons: (1) a single JavaScript/TypeScript codebase spans mobile, web and backend, reducing context-switching for a small student team; (2) MongoDB&apos;s flexible schema suits the wide variety of entities (23 collections spanning academics, transport, and commerce) without heavy upfront migration overhead; and (3) Socket.IO and Redis are lightweight enough to demonstrate real-time features (bus tracking, live notifications) without needing a dedicated message broker such as Kafka at the academic-prototype stage.

11. Advantages and Limitations

11.1 Advantages

Consolidates fragmented campus services into a single, role-aware platform.

Improves transparency via real-time attendance, bus tracking and notifications.

Reduces manual/paper-based processes for complaints, leave applications and placements.

AI assistant reduces time spent navigating menus for common queries.

Modular architecture allows incremental rollout without redesigning the core system.

11.2 Limitations

Phase 1 academic delivery covers six of the twenty designed modules; remaining modules require further development effort beyond the project timeline.

Live bus GPS tracking requires physical hardware (GPS-enabled devices on buses) for real-world deployment, which may be simulated during academic demonstration.

AI assistant accuracy depends on the quality and completeness of the retrieval data set; it is not a substitute for authoritative administrative decisions.

External platform integrations (LeetCode, Codeforces, etc.) depend on third-party API/scraping stability.

12. Future Enhancements

Migrate to a microservices architecture with an API Gateway (e.g., Kong or AWS API Gateway) as module count and traffic grow.

Introduce Kafka for event-driven notification and analytics pipelines across modules.

Add Kubernetes-based orchestration for horizontal scaling of backend services.

Extend the AI assistant with voice input and multilingual support (Tamil/English).

Add predictive analytics for placement readiness scoring and attendance-risk early warning.

Integrate biometric/NFC hardware for the Digital Student ID module for physical access control.

Build an alumni-funded scholarship/referral marketplace on top of the Alumni Network module.

13. Conclusion

CampusOne addresses a genuine, widely-experienced problem — the fragmentation of everyday campus services across disconnected tools — with a unified, role-based, AI-augmented platform. By phasing delivery into a focused Core set of six modules for academic submission and a fully documented Roadmap for the remaining fourteen, the project balances technical ambition with realistic execution within a final-year timeline. The chosen technology stack builds directly on established full-stack and cloud skills, while the AI assistant and real-time features demonstrate applied competency in modern software engineering practices — positioning CampusOne as both a credible academic deliverable and a foundation for a genuinely deployable campus platform.
